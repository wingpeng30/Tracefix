# V0.6.0：真实 Issue Repo Map 单次配对预筛选

## 目的

离线文件定位结果改善后，本阶段先在 3 道固定真实 Issue 上检查 Repo Map 是否值得进入更昂贵的
重复实验。它不是成功率结论：每题每组仅运行一次，模型输出仍具有随机性。

## 固定条件与唯一变量

- 任务、固定源码 commit、任务内容哈希、模型、预算、独立测试环境和 32k 上下文压缩配置均相同；
- 每题执行两次：control 为关闭 Repo Map，treatment 为开启默认 Repo Map；
- 运行顺序按任务交替 `C/T`、`T/C`、`C/T`，以减弱服务时间与缓存顺序影响；
- 两组都保存脱敏的实际模型请求视图，并在 Agent 结束后于干净 checkout 执行 Agent 看不到的隐藏验收；
- Agent 不会看到 `expected_source_files`。评测器仅从轨迹计算首次读取目标文件的步骤和工具调用序号。

## 命令

```powershell
.\.venv\Scripts\python.exe -m tracefix.cli real-repo-map-prescreen `
  --tasks benchmarks/real_tasks `
  --source-root runs/real-task-validation `
  --test-env-root runs/real-task-envs-v2
```

命令会产生 API 费用，并逐 trial 覆盖写 `repo-map-prescreen-summary.json`，因此中断时已完成的
运行仍可审计。它禁止附加 `--repo-map` 或 `--no-repo-map`，避免把两组误配成同一策略。

## 判读规则

记录 Agent 正常结束、公开测试、隐藏验收、是否修改测试、resolved、Token、费用、首次读取目标
文件与请求视图。只有在结果显示定位行为或独立验收有稳定差异后，才应继续做每组至少 3 次的正式
配对实验；否则应先修正任务或 Repo Map 排序，不把一次差异宣传为改进。

## 实际结果（2026-09-11）

完整本机汇总为
`runs/real-repo-map-prescreen-20260911T090649Z-dcea34bb/repo-map-prescreen-summary.json`；可提交的
脱敏聚合数据见
[`benchmarks/experiments/v0.6.0-real-repo-map-prescreen.json`](../../benchmarks/experiments/v0.6.0-real-repo-map-prescreen.json)。

| 组别 | Agent 正常结束 | 隐藏验收通过 | resolved | 输入 / 输出 Token | 费用（美元 / 人民币估算） | 首次读取目标文件 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 关闭 Repo Map | 0 / 3 | 1 / 3 | 0 / 3 | 252,744 / 4,353 | $0.022565352 / ¥0.16247053 | 3 / 3，平均第 2.00 步 |
| 开启 Repo Map | 0 / 3 | 0 / 3 | 0 / 3 | 258,750 / 3,973 | $0.021216600 / ¥0.15275953 | 3 / 3，平均第 1.33 步 |

两组 6 次运行均因 80k 累计输入 Token 上限中断，且没有一次达到 32k 历史折叠阈值。Repo Map
在 Pylint、pytest 上把首次目标文件读取提前到第 1 步（控制组第 2 步），但在这个极小样本中没有
形成完整的“读取—补丁—测试”闭环。关闭组的 pytest trial 虽有可应用源码改动且隐藏验收通过，仍在
模型未正常结束、未运行公开测试的情况下被严格判为未解决。

因此不得把这次 0/3 解释为 Repo Map 使修复率下降，也不应进行昂贵的每组 3 次正式重复实验。下一步
优先修复真实任务中“大量搜索/阅读消耗输入预算而未进入补丁测试”的 Agent 轨迹：限制搜索返回量、把
Repo Map 候选转为更强的首轮行动提示，并在已产生最小补丁时优先要求测试和收尾。之后再在同一固定
任务上重新预筛选。
