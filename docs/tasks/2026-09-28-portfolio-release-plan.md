# TraceFix 作品集交付计划（2026-09-28）

## 用户目标与优先级

用户明确将“尽快交付可用、可演示、能形成简历亮点的项目”设为最高产品目标。
本计划取代旧路线中“先完成全部历史环境诊断，再开展实验，最后做展示”的执行顺序。
默认面向 AI 应用开发 / Python 后端岗位，突出 Agent 系统设计、执行隔离、可观测性和工程交付。
算法提升是后续可选目标，不再作为第一个可展示版本的发布条件。

## 当前起点

- 运行能力：单 Agent、强类型工具注册、搜索/读取/补丁/测试/Diff、独立工作副本、轨迹、Repo Map、上下文管理、按需 Skills。
- 工程：代码候选 `1882cc9` 的 CI run `36420487054` 全部通过；Windows Python 3.11/3.12 各 646 项、0 skip，pytest-only 覆盖率 `11158/12388 = 90.07103648692282%`；editable、wheel、Docker 两臂及基础隔离/清理审计通过。
- 文档提交 `8353395` 的 CI run `36421377177` 也已通过。前述代码候选与本提交运行源码相同。
- 当前 `tracefix-reproduce` 使用脚本模型，证明控制流；不等同于当前版本真实模型自主修复。
- 普通 `tracefix run` 已存在；当前正式 P2 实验的可信 Token 请求前计数仍有门槛。普通运行不因此获得精确费用硬上限，也不得以普通入口绕过本会话的付费限制。
- Docker 支持冻结任务和公开合成配置；不能宣称任意仓库已支持安全容器执行。
- 最大交付缺口：首次使用路径不够聚焦、JSONL 难以展示、缺少整理好的真实案例与作品说明。

## 必须形成的三项成果

### A：可运行、可视化的完整演示（第一批）

在现有 Runner 和 reproduction 入口上做一个完整公开示例。优先沿用现有 fixture 和轨迹结构，
仅在确实无法解释定位过程时增加一个小型多文件 Python 示例，不重写 Agent。

新增轻量报告入口（拟 `tracefix report --run <目录>`），输出无需部署服务的单文件 HTML：

- 任务与执行模式：脚本模型、历史真实模型回放、当前真实模型运行必须明确标注。
- 时间线：失败证据、搜索/读取、补丁尝试、测试反馈和最终状态。
- Diff、测试结论、实际模型 usage（如有）、Token 估算（单列）、耗时、调用数及 Skills 加载事件。
- 所有展示数字取自轨迹和结果；没有的数据标为缺失，不合成模型推理或伪造实时运行。
- 补丁/日志作为不可信文本转义；公开示例进行凭据和本机路径脱敏。

同时修正一个直接影响展示的交付缺口：当前 Docker CI 上传规则只匹配臂目录下的顶层轨迹/补丁，
实际产物位于 `runs/<run-id>/`。补齐这些必要文件的上传与存在性检查，使报告不依赖开发机历史路径。

完成标准：新环境按指南运行公开示例并打开报告，能在两分钟讲解中看懂完整修复链；
失败/预算停止与测试通过能明确区分。演示不要求用户准备 API Key。

### B：真实案例与最短使用路径（第二批）

先从已允许的普通开发任务中整理一个证据完整的真实 Agent 成功案例，以及一个有解释价值的失败案例。
复用现有原始运行与独立验收，记录原代码、任务、模型和限制；不把 gold patch 或脚本应用保存补丁当成模型生成。
这些是选定案例，不计算样本代表性的成功率，也不把历史模型运行写成当前版本新运行。

每个历史案例最多用两小时确认工件齐全；缺项则换用已有完整案例，不为演示重建整套历史任务环境。
若没有合格真实案例，明确此项待补，并准备一个普通 Python 仓库的最小真实运行方案。
任何新增付费调用仍须取得明确的范围和预算授权；本次规划不构成该授权。

整理安装、离线 demo、对自己的受信任 Python 仓库运行、查看报告/导出补丁四条路径。
先处理实际阻断这些路径的安装、参数、错误提示和环境预检问题；原仓库保持独立工作副本流程。
通用本地运行与当前有限的 Docker 支持范围分别写清。当前版本真实模型运行尚未经新调用验证时必须明示。

完成标准：至少一个真实案例可追溯，使用命令可复制，陌生使用者不用先阅读实验历史。
无供应商调用的验收完成后，若仍缺当前真实运行证据，可先交付明确标为离线演示/历史回放的预览版。

### C：作品集与交付包（第三批）

- 重写 README 首屏：解决的问题、演示截图/动图、最快运行命令、支持边界、工程证据链接。
- 提供一页架构图、关键设计取舍、两分钟演示脚本和三条简历描述；完整实验历史移至二级导航。
- 形成可下载 wheel、公开示例、报告和使用指南的候选交付包；版本号在发布准备时统一。
- 现有 PR 的最终代码运行必要测试和 CI，确认后形成候选；合并 PR / 正式发版仍遵守已有授权边界。

完成标准：面试官一分钟内能判断项目做什么，用户能运行演示，作者能解释三处具体技术设计。
新增生产代码按影响补测并保留既有 90% 门槛；通过后不因无关历史兼容性问题反复重跑整个系统。

## 节奏与停止规则

- 建议以三个各约一个工作日的交付批次推进；这是时间盒，不是已测工期。优先压缩范围，不扩展平台和任务数。
- 每个批次必须交付可查看的产物：报告页面 → 案例与可复制命令 → README/演示与候选包。
- 新任务只有直接改善演示、首次运行、补丁可信度或已承诺的安全边界时，才能插入第一优先级。
- 同一非核心环境问题诊断超过两小时仍无明确进展，记录限制并换用受支持示例，不降低测试判定标准。
- 第一版达标即冻结范围；工程检查失败才修复、重跑受影响检查。收到真实使用反馈后再选择一个改进点。
- 当前继续零供应商调用，不访问留出题，不改写历史证据、评分或账本。

本次只完成目标重排与计划落盘，未添加产品功能、运行实验或变更已有验收结论。
