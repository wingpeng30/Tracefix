## 主要发现

### 1. 高优先级：正式汇总仍漏报运行事故

原始第 59 项 `stop_reason=agent_error`，运行结果明确保存 Windows 账本替换 PermissionError，但 trial 状态为 `verification_complete`。当前 `summarize_p2_experiment()` 只按 `record.status == "infrastructure_error"` 统计事故，因此本次重算仍得到事故 0；`diagnose_p2_experiment()` 对相同工件得到事故 1。

代码位置：`src/tracefix/p2_protocol.py:923` 附近；机器结果 `benchmarks/experiments/v0.8.6-p2-formal-rerun.json:7` 仍写 `infrastructure_failures: 0`。中文报告已经更正，但更正没有贯穿自动汇总和发布的机器结果。当前状态不能宣布“证据汇总已完全收尾”。

建议独立保存运行终止、基础设施状态、验收状态三个维度；事故统计不得被完成验收遮蔽。保留历史原件，通过带来源与替代关系的更正工件提供统一有效口径，并增加“发生事故但仍有验收记录”的汇总回归。

### 2. 高优先级：提示与验收规则冲突影响超过半数试次

60 项中 32 项因测试或配置改动被拒绝：28 项同时改产品源码和测试，3 项仅测试，1 项涉及配置。C 17 项、T 15 项。严格验收在识别这些改动后直接返回，不能推断其余产品源码补丁原本会通过，也不能把 32 项都解释为算法未能修复。

新提示已经明确禁止这些改动，属于必要修复；旧结果仍需原样保留。双方同受冲突影响并不保证偏差抵消，因为策略可能改变添加测试的频率与内容。新提示版本的能力结论必须由独立新批次支持。

### 3. 高优先级：核心机制效果尚不可归因

C 同时关闭行动优化、Repo Map 和压缩，T 同时开启；T 组有 30/30 Repo Map 和 662 次工具结果精简，但历史折叠为 0。当前只能评价这一整体配置的探索性结果，无法识别哪个模块有效。

早期 V0.4 与 V0.7.3 自然多文件报告已经指出 32k 未触发的问题，说明这是持续的实验适配问题。若继续研究压缩，应先确定能自然触发机制的独立任务层；若研究行动优化与检索，应分别消融，避免将总体差值解释为压缩收益。

### 4. 中优先级：诊断对缺失验收证据的默认分类不严谨

静态检查发现，`diagnose_p2_experiment()` 在验收文件不存在时保留空字典，随后使用 `verification_payload.get("reason") or "passed"`，可能在失败原因统计中把缺失证据记为 passed；函数也没有调用恢复路径已有的 `_verify_saved_artifacts()`。这不直接改变 `independent_passed`，但会污染诊断分类与可信度。

本批 180 个工件哈希完整，未观察到该问题实际影响本批统计。建议缺失/损坏/哈希冲突单列为 evidence_error，不默认通过，并对结构化 eligible/status 进行交叉验证。

### 5. 中优先级：测试数量与综合覆盖率不足以证明可靠性收尾

已有 280 项通过和异常路径测试是优点；但约 90.14% 为综合覆盖率，分支覆盖率实际约 81.41%，不能表述为“分支覆盖率达到 90%”。当前全量通过的同时仍存在上述汇总口径缺陷，说明指标之外还需要针对真实事故形态的回归。

`p2_protocol.py` 约 1,870 行，集中承担协议、账本、执行、恢复、汇总、诊断等职责；`real_experiment.py` 约 1,774 行，CLI 约 1,051 行。职责集中增加后续修改影响范围。建议先补行为回归，再按职责拆分，不以重构替代实验。

### 6. 中优先级：版本、文档和复现入口不同步

README 自称最新开发版本 v0.8.3，包元数据和运行时版本仍是 0.8.4，实验文档已经到 v0.8.6。提交哈希能帮助定位，但首次读者难以知道哪个命令和结论代表当前状态。

原始工件主要位于本机忽略目录，包含绝对路径；配方和哈希提升了本机可审计性，但尚不等于另一台机器已复现。Git 状态还遇到多处旧临时目录访问拒绝。应整理证据索引和可移植的复现入口，保留现场，不自动清理权限异常目录。CI 只有 Windows 两个 Python 版本的配置，本次未验证远端执行结果；跨平台可信度仍有限。

## 对工程与研究质量的评价

工程优点是验收边界较细：新 checkout、独立测试、JUnit 与收集/执行审计、真实导入路径、冻结 node ID、依赖漂移，以及费用预留、请求身份和恢复。实验记录也主动区分资格、合成、离线定位和真实修复，并保留失败尝试。这些比单纯展示成功轨迹更有价值。

不足集中在三处：汇总口径尚未一致；实验协议与 Agent 实际行为未在付费前充分对齐；小样本整体对照无法支持预期的机制与泛化结论。当前可以称为“有真实实验和审计底座的研究原型”，尚不能称为“已验证能稳定降本提效的修复系统”。

## 建议的推进顺序与验收标准

1. 先统一 summary、diagnostic、中文和 JSON 结果；相同输入必须得到相同事故数，缺失证据必须显式失败。
2. 将提示规则、正式评分规则和预算终止行为做成端到端回归；新执行版本单独冻结，不追溯修改旧评分。
3. 用既有轨迹完成 Repo Map 命中、读取行为、工具结果精简与失败路径分析，建立下一轮可证伪的单项假设。
4. 再进行有新版本、新任务身份的单项消融和留出集评测；报告任务级波动、成功率和完整计时边界。压缩机制必须先证明实际触发。
5. 统一版本入口、覆盖率术语和证据索引，验证跨机重建；达到这些门槛后再考虑正式发布或同条件外部基线比较。

这些是监察建议，本次没有执行修复、追加付费实验或发布操作。
