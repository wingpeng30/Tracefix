## 从原始工件得到的具体发现

### 1. 环境故障已有更具体的定位，不能继续只写“网络/报告问题”

Requests 六项日志中，目标 URL 是本地 `127.0.0.1:8765`，但代理表包含 `http://127.0.0.1:9`，连接此代理被拒绝。第 3 项的 `execution.stdout.txt` 同时保存了目标、代理表和 ProxyError。已确认的是请求没有正常直达测试服务；不能据此断言服务自身是否健康，或代理最初由谁注入。

Sphinx 全部 12 项在缺报告之前出现 PermissionError；抽查第 13 项显示 fixture 在取得 `.tracefix-build-tmp/pytest-of-PengZixuan` 基目录时失败。pytest-10081 第 26、41 项同样有权限错误。报告缺失是后续症状，优先检查执行身份、临时目录权限与隔离边界。日志不能单独区分 ACL、沙箱、旧目录所有权或其他 Windows 机制，故不宣称底层原因已复现。

建议：在同一执行身份及实际子进程环境下检查服务路由和临时目录，再用固定 base/gold/已有补丁复验。处理代理必须尊重平台网络策略；若当前执行环境不允许所需能力，改用获准的隔离评测环境，不在被测 Requests 源码中绕过。

### 2. 工具把自己的审计产物混入补丁和模型上下文

保存补丁按 `diff --git` 分块后，第 **5、13、14、21、30、45** 项全部只涉及 `.tracefix*` 路径，没有其他仓库文件差异。第 5、21 项却被原验收分类为 pytest execution failed；这使“没有产生产品改动”和“产生了错误改动”混在一起。此处保留旧分类，只添加诊断标签。

代码链路也支持这个观察：`GetGitDiffTool` 收集所有未跟踪文件；测试审计写在 checkout 内；Agent 用整个 diff 是否非空更新 `_diff_nonempty`；独立验收的空补丁检查只判断补丁文件是否为空。这样，工具产物能够满足“非空”的形式条件。并不意味着这些试次被独立验收误判通过。

**19/48 个试次**的后续模型请求视图中实际包含 `.tracefix-test-tmp` 的 diff 正文，不只是最终归档文件较大。全部保存补丁共 7,164,759 字符，去除 `.tracefix*` 分块后剩 41,673 字符；字符数不是 Token，不能把这个比例解释成可节省 99% 输入。

建议：审计工件存到 checkout 外的受控目录；分别定义产品源码差异、允许的文档/配置差异和工具内部产物；模型 diff 视图与最终补丁导出共用明确边界。先用“仅运行测试，没有改源码”的零费用回归检查：产品 diff 必须为空，模型请求不得含审计文件正文。不要只靠宽泛忽略规则让 Agent 能隐藏任意改动。

### 3. 预算和反馈让许多尝试在修复完成前停止

最新批次原始 Agent 终止状态是：正常完成 7、单请求上界拒绝 21、累计输入预算预拒绝 16、测试额度耗尽 3、操作事故 1。这与最终验收分类是两个维度：预算停止的补丁仍可能正确，不能把 37 次资源停止全部计为预算导致的修复失败。公开摘要按证据问题优先分类后只显示 9 个 request_bound_violation，隐藏了另外 12 个试次的 Agent 阶段停止原因。

DeepSeek 分支 `count_input_tokens` 返回序列化请求 UTF-8 字节数加 1,024，以此执行 128,000 单请求上界以及剩余累计预算预留。它是保守财务边界，不是实测 Token。21 项被拦截前最后一次成功响应的实际输入为 15,846–35,370 Token；这不是被拒下一次请求的真实 Token，因此只能证明不能把拒绝直接描述为模型已用满 128k。

代码还在命令验证前递增 `test_runs`。V0.8.19 第 38 项曾连续拒绝四条 `python -c`，最终六次额度耗尽且没有补丁；当前代码仍保留这一计数顺序。最新批次也看到两条同类命令拒绝。只有 pytest 的工具接口、禁止新增测试、把被拒命令计入执行额度，组合起来限制了最小问题复现。

建议：先清除审计 diff 噪声，区分实际 Token、保守预留与上下文长度；命令参数错误和真正启动的测试分别计数，同时保留独立的总步数限制。若增加复现脚本能力，应在隔离环境和独立临时目录中执行，不修改隐藏验收测试。不要直接删除费用保护或笼统加大预算。

### 4. 真实语义失败存在，但提醒机制没有针对性

pytest-10356 第 11 项已改到 `src/_pytest/mark/structures.py`，尝试合并继承标记，但验收保存了“generator 与期望列表比较失败”的断言。补丁保留了 `return normalize_mark_list(...)`；第 12 项通过补丁返回 `list(...)`，也有其他 MRO 处理差异。因此这里存在超出定位的语义/契约问题，不能说补上一个 list 就保证完整修复，更不能把它归为搜索不足。

Pylint 两项包含 setup.cfg 修改而被策略拒绝。setup.cfg 同时可以承载包装依赖和 pytest 配置，受保护路径拒绝不自动意味着模型企图改测试；若未来调整规则，需要按配置节区分，保持隐藏验收不可修改。

旧批次的两个 pytest-10081 T 空补丁反复提交同内容直到耗尽预算，闭环结束提醒完全没有触发；全批也只有两个 T 试次触发提醒。因而“提醒没改善”不能证明验证思路无效，但足以说明本次处理没有覆盖主要失败路径。合成脚本会按设计重读、换补丁，证明的是控制流可执行，不能证明真实模型会更好地修复。

## 建议的推进顺序与明确出口

1. **先完成已有资产的收尾。** 对 20 项不确定结果建立补丁原字节、固定源码与验收配方索引；优先修清两类环境契约（代理路由、临时目录），在同一获准环境中对 base/gold/旧补丁重复验收，另存结果。若重复结果仍不一致，不继续新增付费整批；转到 Linux 容器评测试点。只复验能够挽救最终评分，无法挽回 Agent 当时收到的坏反馈，因此不把抢救结果当成干净环境的效果实验。
2. **只修已有证据的基础契约。** 首选移出审计工件、修正产品 diff 口径；其次区分无效调用和实际测试额度。用现有轨迹及小 fixture 检验。工程回归通过仅代表该缺陷修正，不重新包装成模型成功率提升。
3. **把下一次研究问题改成“自研控制层究竟有没有帮助”。** 环境稳定后，先在 4–6 道有代表性的已看开发题上做 TraceFix 基线与 mini-SWE-agent 的同期小比较，固定模型、资源上限、独立验收器。这是诊断试点，不是显著性结论，也不是重新启动 48 项批准流程。
4. **按结果选方向。** 若同模型的简单基线明显更好，优先删减自研约束、借用成熟运行器；若两者在相同语义问题上失败，再单独评估推理模式/更合适编码模型，不能预先归咎于 DeepSeek；若两者都能修复，才研究 TraceFix 能否以更少 Token/时间保持成功率。
5. **重新聚焦项目价值。** 更有证据基础的候选方向是“可解释的失败分类与预算分配”，用已有轨迹解释定位失败、无产品改动、错误改动、验证失败、环境失败各自的成本。上下文压缩仍可保留，但真实开发批次历史折叠为零时，应先找自然长轨迹验证机制覆盖，不能用合成长上下文成功宣称真实修复收益。20 题留出集继续封存到配置选定。

这些是方向建议，本轮没有安装参考项目、切换平台、改 Agent 或启动付费比较。

## 统计解释与限制

按 ARS 方法检查 11/11 类统计谬误：聚合与分层方向（没有据此断言辛普森反转）；生态推断（8 题不能代表所有真实 Issue）；筛选/Berkson 风险（资格筛选与仓库构成限制外推）；碰撞偏差风险（只留证据有效子集可能引入选择）；基础率（保持固定分母）；回归均值（不能只看最差失败后的改善）；幸存者偏差（不得丢掉 20 项）；多重探索（多轮挑配置）；分析路径选择（本轮新分类是事后探索）；相关与因果（轨迹分歧不是处理效果）；反向因果（更难任务可能同时更耗 Token、更容易失败）。未发现某类谬误，不等于已证明不存在偏差；本轮不计算显著性或给出提高幅度。

只有 8 道独立普通开发任务，重复 3 次不能解释成 24 道独立任务。多轮开发探索后，最终确认要按任务聚类，保留失败与不确定位置，并使用未用于调参的样本；不能跨不同模型、执行权限、环境与预算直接比较百分比。

已验证的是保存工件的完整性、代码路径和日志事实；未验证的是环境修正后的旧补丁成绩、上述修正的因果收益、其他模型上限，以及参考框架在本机的兼容性。本轮的实际改动仅为本报告与派生 JSON。
