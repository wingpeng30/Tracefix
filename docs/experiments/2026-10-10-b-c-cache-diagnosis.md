# B/C 供应商缓存差异逐请求诊断

2026-10-10，只读分析上一轮同一30题的747次请求尝试，其中745次有已知响应（B409、C336），C另2次响应未知。未发送供应商请求，未重跑任务或调整产品策略。产品基线为`e380329d2a007a83dd317944bafd426d4b829c82`；本轮只补充已有实验的机制诊断。

结论：缓存下降主要指向C在静态材料之前插入并更新的动态测试事实锚点，而非本批确定性工具结果裁剪。代码`src/tracefix/agent/minimal.py:337`构造`(full_history[0], anchor, *full_history[1:])`，把动态事实放在第二条消息。后面的Repo Map、约百万字符静态材料和工具历史虽然没有改变，其前缀仍会因此失配。B的历史只追加，没有此锚点。

DeepSeek官方文档说明缓存按前缀单元匹配，前缀必须完整匹配已落盘单元；构建为秒级、尽力而为，不保证全部命中。参见[上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)。以下是实际请求和供应商返回用量统计；消息内容公共前缀另用字符代理测量，不将其冒充官方Token前缀长度。
