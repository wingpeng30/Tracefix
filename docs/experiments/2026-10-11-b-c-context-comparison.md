## 时间为何增加

主耗时统一取`timings.delivery_seconds`：工作区准备完成到独立验收结束。`record.seconds`包含准备与Agent运行，却不等于这个口径；下表使用交付字段及各阶段原始计时，不混用。准备时间另列，不能加进主耗时解释。

Agent其余时间按Agent总时间扣除供应商、计数、工具与补丁计算；C Repo Map索引205.8秒包含在这一项内。计时嵌套及少量外围壁钟差使各行与总量存在亚秒级差，不宜进一步机械相加。C的`context_preparation_seconds=2065.1`及`model_request_seconds=4922.9`包含上述计数/请求阶段，不可再计入总量。

**最主要的是本地官方计数开销增加，贡献总时间增量的74.3%。** 核对当前以下6个源码文件的哈希与冻结C清单全部一致，执行路径为：

1. `agent/minimal.py`请求前调用`ContextManager.prepare(..., token_counter=self._count_context_tokens)`，用于窗口检查。
2. `context/manager.py`按完整内容哈希缓存自身计数；新增消息或裁剪后的不同投影仍需要计数。
3. `comparison.py`的`PaidLLM.complete`随后为付费准入再次调用`count_input_bound`。适配器没有与ContextManager共享已完成的输入计数，导致同一投影可重复编码。
4. `comparison_profiles.py`的`OfficialCounter.count`每次通过`subprocess.run`启动冻结的WSL/Python worker。
5. `comparison_counter.py`每次启动重新哈希tokenizer与deepseek-recipe/pydantic/pydantic-core依赖文件，然后加载tokenizer、编码、输出、退出。`models/input_bounds.py`虽有进程内加载缓存，跨这类一次性worker无法复用。

因此，原计划的“会话固定身份、复用已加载tokenizer”没有在付费评测的WSL计数接入中落实；窗口检查和费用准入也没有共享计数。这里是集成效率问题，不是为了保留保护而必须每步重启进程。日志未记录每次worker启动次数及各内部子阶段，因此不能精确拆出其中加载、依赖哈希和编码各占多少；确认的是计数总时间及上述重复路径。

供应商时延也增加：请求数减少409→315，平均单请求却从6.73→10.56秒（+56.9%），使累计多573.3秒。C每请求平均输入多约4.5%、输出多7.3%、未命中输入多46.7%，可能增加预填充和生成时间。但实验非同期，没有首Token时延、网络或服务器排队分解；相同模型/fingerprint不能证明运行负载相同，因此不能把全部573秒归因于缓存率。

本批真实压缩次数为0，所以“压缩反复运行导致变慢”不符合证据。工具执行反而节省307秒，较少补丁尝试与搜索符合更少交互的观察。
