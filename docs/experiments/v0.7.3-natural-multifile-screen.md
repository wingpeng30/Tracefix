# V0.7.3：非重复多文件任务的 32k 触发筛选

## 候选集与目的

本次使用 `benchmarks/context_tasks/` 的四道多文件合成任务作为候选集：

- `config_precedence`：request、tenant、environment 与 default 的配置优先级；
- `event_merge`：身份规范、冲突胜者和 payload 合并；
- `retry_pipeline`：错误分类、重试预算与退避；
- `shipping_route`：区域、温控、重量和稳定排序。

这些任务的规则分散在多个真实 Python 模块，并带 Agent 不可见的隐藏测试；内容不是通过重复
文档填充出来的。它们仍是合成任务，不能表述为真实 GitHub Issue。

筛选目标不是比较处理组效果，而是判断这些自然多文件轨迹是否会在生产 32k 阈值下产生历史折叠。
每题只运行一次开启 Token 优化、开启上下文压缩的组；Agent 自主决定读取范围。

## 固定条件

- 模型：`deepseek/deepseek-v4-flash`；
- 累计输入预算：350,000 Token；最大 24 步、6 次 Agent 测试；
- 上下文折叠阈值：32,000 Token；
- 每题在独立 Git 工作区运行，完成后执行公开和隐藏验收；
- 保存脱敏模型请求视图。

## 结论

候选集的代码与测试反馈确实使 Agent 阅读了 6–7 个文件并完成修复，但每次模型请求只保留
约 4–6k Token。TraceFix 的 Repo Map、工具结果投影和短闭环使历史没有自然累积到 32k。

因此四题应保留为**准确率、行动效率和隐藏验收**基准，但全部拒绝进入“关闭压缩 vs 32k 压缩”
配对实验。下一批压缩候选必须来自更大、真实仓库，并在单次筛选中同时满足：

1. 至少一次请求估算达到 32k 且实际发生历史折叠；
2. 至少读取五个与业务约束直接相关的文件；
3. 包含补丁后的测试反馈或修复调整；
4. 固定 commit、任务文本、隐藏验收和干净 TraceFix commit。

不能通过强迫读取重复文本来满足这些条件。
