## 更正后的执行分类

原报告的“60/60 项完成”表示每个计划位置都有独立验收记录，并不表示 60 次 Agent 都正常结束。
按运行结果重新分类后：24 次由 Agent 主动结束，12 次达到步骤上限，5 次达到测试上限，17 次在
下一次供应商调用前正常耗尽单项输入预算，1 次触发单请求输入上界，1 次发生 Windows 账本原子
替换 `PermissionError`。因此基础设施事故应为 1 次，而非 0 次；第 59 项的空补丁验收结果不能遮蔽
这次基础设施事故。

预算停止现在使用独立的 `p2_trial_budget_exhausted` 状态，后续不会再笼统记作
`benchmark_error`。账本写入改用唯一临时文件，并对 Windows 短暂占用进行有限重试；重试不涉及
供应商请求，持续失败仍会保留失败并停止。

## 32 项测试修改拒绝

严格验收拒绝了 32 个修改测试或 pytest 配置的补丁。其中 28 个同时修改产品源码和回归测试，3 个
只增加测试或探索文件，1 个同时修改 `setup.cfg`。这说明主要矛盾是 Agent 提示允许在修复时增加
测试，而 P2 独立验收禁止任何测试改动。后续 P2 配置已明确告知 Agent 不提交测试、conftest、
pytest 配置或 `setup.cfg` 改动；独立验收规则本身保持不变。旧 32 项仍按原规则判失败，不追溯改判。

## 机制是否实际启用

两组各 30 项。T 组 30/30 生成 Repo Map，并有 662 次工具结果精简；C 组没有 Repo Map，也没有
工具结果精简。两组上下文折叠次数和因上下文管理裁剪的工具结果均为 0。因此本轮 T−C 输入
Token 差异可以作为“三项整体配置”的探索性结果，但不能归因于 32k 上下文压缩。压缩阈值在这批
轨迹中没有形成处理差异。
