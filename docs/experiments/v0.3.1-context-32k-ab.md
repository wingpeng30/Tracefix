# V0.3.1：关闭压缩 vs 32k 压缩

## 实验设计

本实验在同一 TraceFix commit `247a881` 上，使用相同模型、两道长上下文合成任务和相同
预算，比较完全关闭上下文管理的对照组与启用生产默认 32k 软阈值的实验组。每题要求分批
审计 24 份仓库契约，再修改实现、运行测试并检查 Diff。

脱敏机器可读结果见
[`benchmarks/experiments/v0.3.1-context-32k-ab.json`](../../benchmarks/experiments/v0.3.1-context-32k-ab.json)。

## 聚合结果

| 指标 | 关闭压缩 | 32k 压缩 | 变化 |
| --- | ---: | ---: | ---: |
| Resolved | 2/2 | 2/2 | 不变 |
| 正常完成 | 2/2 | 2/2 | 不变 |
| 输入 Token | 370,387 | 185,587 | -49.89% |
| 输出 Token | 5,135 | 4,598 | -10.46% |
| 模型步骤 | 24 | 22 | -8.33% |
| 工具调用 | 68 | 65 | -4.41% |
| 运行耗时合计 | 47.891 秒 | 41.985 秒 | -12.33% |
| 美元费用 | $0.03506432 | $0.031672856 | -9.67% |
| 人民币估算 | ¥0.25246310 | ¥0.22804456 | 节省 ¥0.02441854 |

实验组发生 5 次历史折叠，累计折叠 160 条消息、37 个工具批次，本地估算节省
228,165 Token。两组都没有工具失败或完全重复调用。

## 最有说服力的配对证据

`long_policy_window` 的两组轨迹都完整读取了同样的 24 份契约，工具调用分别为 32 和 34，
模型步骤分别为 11 和 12。实验组甚至多一次模型请求，但在第 8 步开始折叠历史，共发生
5 次折叠，实际输入 Token 从 260,867 降到 105,154，下降 59.69%。这比只看聚合结果更能
说明折叠机制确实减少了发送给供应商的历史，而不是依靠更短的探索路径。

对照组最后几个请求的本地上下文估算逐渐增至约 56k；实验组折叠前也达到约 56k，但折叠
后的请求视图稳定在约 10.7k～11.7k，同时仍然正确修复并通过测试。

## 需要分开解释的结果

`long_route_normalization` 两组都访问了 24 份契约，但模型只完整读取前 4 份，之后只读取
每份文档的契约结论行。实验组没有触发历史折叠，只对较长工具结果进行了裁剪；同时它比
对照组少了 3 个模型步骤。因此该题输入 Token 下降 26.56% 是“工具结果裁剪、路径随机性、
步骤减少”的混合结果，不能单独归因于历史折叠。

聚合输入 Token 几乎减半，但费用只降低 9.67%。当前保存的 usage 无法拆分缓存命中、缓存
未命中以及不同 Token 类型的费用，因此只能确认费用没有与 Token 数量同比下降，不能从这
一次实验判断具体计费原因。

此外，`tool_results_pruned=41` 是各次模型请求中重复执行裁剪的累计次数，不代表 41 条唯一
工具结果被裁剪。这个指标适合衡量压缩器工作量，不适合当作唯一消息数。

## 结论

这次实验初步支持以下结论：在保持 2/2 解决率的情况下，32k 确定性上下文管理可以显著
降低长轨迹的实际输入 Token。`long_policy_window` 提供了较强的同任务配对证据。

但样本只有两题、每个条件只运行一次，并且任务为了触发长上下文而明确要求分批审计契约。
因此结果应标记为机制验证，不应直接宣传为真实 Issue 上平均节省 49.89%。下一步应重复每组
至少 3 次，并加入自然产生长日志、多次失败测试和跨文件调用链的真实仓库任务。
