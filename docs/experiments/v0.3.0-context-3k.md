# V0.3.0：3k 上下文压缩实验

## 实验目的

本实验验证确定性上下文压缩在相同模型、任务和预算下，能否减少供应商实际输入 Token，
同时保持 V0.2.0 Baseline 的修复率。这里将压缩触发阈值故意降到 3,000 Token，
`retain_ratio` 设为 0.4，用于让 10 个小任务也能触发压缩。生产默认仍为 32k，3k 不是
模型上下文上限，也不应作为生产推荐值。

实验使用 `deepseek/deepseek-v4-flash`、10 个合成 Python Bug、每题最多 12 次模型请求、
40k 输入 Token、8k 输出 Token、5 分钟和 4 次 Agent 测试调用。完整原始轨迹只保留在
本机 `runs/`；可提交的脱敏数据见
[`benchmarks/experiments/v0.3.0-context-3k.json`](../../benchmarks/experiments/v0.3.0-context-3k.json)。

## 结果

| 指标 | V0.2.0 无压缩 | V0.3.0 3k 压缩 | 变化 |
| --- | ---: | ---: | ---: |
| resolved | 10/10 | 7/10 | -3 |
| 输入 Token | 184,730 | 203,390 | +10.1% |
| 输出 Token | 8,982 | 9,808 | +9.2% |
| 模型步骤 | 74 | 84 | +10 |
| 工具调用 | 87 | 101 | +14 |
| 完全重复工具调用 | 6 | 23 | +17 |
| 费用（人民币估算） | ¥0.18140797 | ¥0.25072877 | +38.2% |

压缩器共准备 84 次请求视图，其中 19 次发生历史折叠，估算节省 17,973 Token。但这是
本地字符估算值，不等于供应商 usage。由于失败恢复带来了更多模型步骤，最终供应商统计的
实际输入 Token 反而增加了 18,660。

## 失败分析

三个未解决任务为 `nested_lookup`、`file_extension` 和 `retry_count`。它们都在 12 步上限
处中断，没有成功修改文件，也没有进入 Agent 内部测试。轨迹显示模型很早就提出了正确或
基本正确的代码修改方向，但 `apply_patch` 反复失败：

- 部分响应使用 `*** Begin Patch` / `*** Update File` 格式，旧工具只接受 Git unified diff，
  因此报错“补丁不包含文件路径”。
- 部分 unified diff 的 hunk 行数元数据不准确，`git apply --check` 报
  “corrupt patch at line ...”。补丁内容本身有可能是可恢复的。
- 工具只返回失败，没有抑制相同失败调用，也没有给出足够明确的格式恢复建议，模型于是
  重复提交相同或近似补丁。

这三个任务的第一次补丁失败都发生在首次历史折叠之前，因此“压缩丢失关键信息”不是最初
失败原因。不过 3k 阈值下的频繁折叠没有帮助模型脱离错误循环，并增加了恢复难度。

`pagination` 是另一种边界情况：Agent 已经修改代码且测试通过，独立评测也判定 resolved，
但模型继续调用工具，直到步骤上限，导致 Agent 状态仍为 `interrupted`。这说明评测结果与
Agent 生命周期完成状态必须分别记录，也说明循环需要一个明确的“测试通过后收尾”信号。

## 结论与启示

1. 当前主要瓶颈不是模型找不到 Bug，而是模型输出协议与工具接收协议之间的兼容性。
2. 上下文压缩应以端到端指标评估；本地“估算节省 Token”不能代替供应商 usage、费用和解决率。
3. 很低的软阈值可能让简单短任务也过早折叠。生产默认继续使用 32k，3k 仅保留为压力实验。
4. 失败恢复要有确定性护栏：兼容常见补丁格式、修正可恢复的 hunk 计数、拒绝重复失败调用。
5. 测试通过且 Diff 非空后，应提示模型立即给出最终回答，避免“已经解决但没有正常结束”。

## 对应修复

后续补丁版本针对这次真实失败增加：Git diff hunk `--recount`、常见
`*** Begin Patch` 更新格式转换、失败补丁重复调用抑制、连续补丁失败恢复提示，以及
“测试通过 + 非空 Diff”的收尾提示。所有改动先使用离线单元测试和失败样本回归验证，
不在修复阶段自动产生新的 API 费用。
