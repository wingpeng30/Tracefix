# V0.4.0 多文件任务：关闭压缩 vs 32k 配对重复实验

## 结论先行

正式 24 个 trial 中，两组均为 12/12 resolved，且 Agent 正常结束、公开测试通过、独立隐藏
验收通过均为 12/12，测试文件修改为 0。可是 32k 组没有任何一次真正触发历史折叠；四题
单次请求的最高本地估算仅为 4,582～8,326 Token。因此本实验不能用于证明压缩提高或降低了
性能，两组 Token/费用差异只能视为模型轨迹随机波动。

机器可读数据：
[`benchmarks/experiments/v0.4.0-paired-context-32k.json`](../../benchmarks/experiments/v0.4.0-paired-context-32k.json)。

## 实验设计

- TraceFix commit：`2c3de4ed3062f4fa9813244d54974afd9b93d9eb`，24 次均记录为干净工作区；
- 模型：`deepseek/deepseek-v4-flash`；
- 任务：4 道多文件语义任务，每题每组 3 次；每题各 trial 的任务 SHA-256 一致；
- 顺序：第 1 轮 C/T，第 2 轮 T/C，第 3 轮 C/T；
- 预算：20 步、120k 累计输入、12k 输出、600 秒、6 次 Agent 测试；
- 对照组完全关闭压缩；实验组启用 32k 软阈值；其余模型、预算、工具与任务一致；
- 所有 trial 开启脱敏实际请求视图记录；
- `resolved` 同时要求 Agent completed、公开测试通过、隐藏验收通过、测试未被修改。

## 行为与失败分析

四题两组都没有重新读取同一文件。对照组唯一的“完全相同参数调用”是 `event_merge` 第二次
运行在修改补丁后再次执行相同的 `pytest -q`；它是有新代码状态后的必要复测，而非无信息
循环。该 trial 首个补丁没有正确处理“胜者是旧事件”时的 loser payload，公开测试失败后，
Agent 增加 loser 选择并再次测试，最终公开与隐藏验收都通过。

32k 组没有历史折叠、工具结果裁剪、折叠后工具失败或折叠后未解决任务，所以不存在可分析的
“压缩后错误决策”。未触发折叠的任务必须全部单列：`config_precedence`、`event_merge`、
`retry_pipeline`、`shipping_route`。

## 无效预运行

正式实验前的 8 个 trial 因评测器把 pytest 生成的 `tests/__pycache__/*.pyc` 误判为测试修改
而停止。它们的 Agent、公开测试和隐藏验收实际都是 8/8，但 resolved 标志无效，未纳入任何
正式指标。该轮产生 $0.044234544，约 ¥0.31848872 的 API 费用。修复方式是忽略缓存产物，
并在四个任务模板中加入 `.gitignore`；正式实验随后固定到新的干净 commit。

## 下一功能决策

本轮没有正式失败，而且没有触发压缩，因此不能根据证据选择以下任何一项：

- 没有旧证据丢失，不能据此改上下文摘要；
- 没有文件定位失败或重读，不能据此证明 AST/Repo Map 是当前瓶颈；
- 没有“公开测试通过但隐藏验收失败”，不能据此继续加强 Patch Verifier。

合理的下一步不是猜一个模块实现，而是引入更大的真实仓库 Issue，或重新设计能在自然探索中
跨过 32k 的语义任务，再使用本版三层验收和请求视图分类失败。只有出现对应失败信号后，才
选择摘要、Repo Map 或 Verifier，避免为了简历堆功能而失去实验因果性。
